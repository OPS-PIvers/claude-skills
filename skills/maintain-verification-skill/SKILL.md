# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill`, or any project-local verification skill with a feature map.

The unit of rigor is the feature, not the sentence. Cover every feature file from source and exercise every feature live. Don't try to prove every bullet with a terminal command.

## Outcomes

End with exactly one of these, and say which:

- **clean:** every feature got source and live coverage and nothing needs changing. No branch, no PR.
- **changed:** one PR ships proven doc, harness, or map corrections.
- **blocked:** coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory: its `SKILL.md`, `features/`, and any harness scripts it owns. Never edit product code during a run.

When the map describes something the app no longer does, it is one of two things. Doc drift means the app changed on purpose, so fix the map. A product regression means the app broke, so report it and leave the map alone. Don't paper over a regression by rewriting the docs to match the bug.

## Pass

### 0. Locate the target

Find the verification skill to maintain: a project-local skill whose body has launch and drive sections and a feature map, usually `.claude/skills/verify-*/`. Also check `.cursor/skills/verify-*/` in case the repo predates the Claude version.

- Several candidates: ask the user which one.
- None: stop and point at `/create-verification-skill`. Don't invent a target.

### 1. Index hygiene

Read `features/README.md` and glob its sibling files. Fix missing, extra, duplicate, or dead entries. This is lightweight; don't generate an inventory.

### 2. Source wave

Launch one read-only subagent per feature file, all in a single message so they run concurrently. Use the `Explore` agent type, or `general-purpose` if Explore isn't available, with a cheaper model when the feature is simple.

Each subagent explains "how does this user-facing feature work?" from source, flags likely doc drift with file and line citations, and returns one concise live-verification recipe. Subagents never drive the app and never edit files; say so in each prompt, since they start with no context.

Give each subagent the feature file's full contents and the path to the verify skill, and ask for exactly this return shape:

```
Feature: <name>
Summary: <2-4 sentences, user POV>
Source entry points: <path:line, ...>
Likely drift: <claim in the map → what the source says, with citation> | none
Recipe: <the shortest live drive that proves the feature end to end>
```

### 3. Reconcile

- Every feature file has a returned summary. Re-run any subagent that came back empty or off-task.
- Merge overlapping recipes into as few app states as practical, so the live pass doesn't relaunch for every feature.
- Spot-check cited drift yourself. Don't re-prove claims the subagents found clean.
- Sweep recent churn (`git log` since the map's last update) for user-facing surfaces missing from the map. Require a concrete source path before calling one missing.

### 4. Live pass

Required even when source looks clean. You, the coordinator, do all the driving; subagents never touch the app.

Follow the verification skill's own launch model; its Launch section decides, not this one. That usually means one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs. Exercise every feature at least once.

Hold three invariants for the whole pass, whatever fails:

1. **Never drive an instance you haven't health-checked since it last surprised you.** Run doctor before the first drive, on each fresh session where sessions are the unit, and again after any failed drive. Where doctor can't see the failure (a wedged UI on a healthy process), reset to a known state or relaunch rather than hoping.
2. **Evidence survives every cleanup.** Check it at its named location; don't assume.
3. **Nothing a drive started outlives its usefulness.** Clean failed-iteration residue whether the session is stuck, exited, or shared. For a shared instance, clean the residue, not the instance. Kill by recorded PID or port, never by process name.

Handling failures:

- A doctor failure caused by skill drift is drift. Fix it within edit scope and retry once, restarting only what the fix invalidated. If it still fails, the pass is `blocked`.
- A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted. If the map doesn't mention that prerequisite, that's drift too.
- Any harness fix from triage gets re-driven live before it ships.
- Final teardown happens after the last drive of the run, including those re-proofs, so nothing outlives the run. Evidence stays, per the skill.

### 5. Triage

| What you found | Classification | Action |
| --- | --- | --- |
| User-POV description is wrong or missing | Doc drift | Fix it in the map |
| Behavior works but the harness can't drive it | Harness gap | Fix the harness. Scripts must be runnable and their invocation shown in the skill body, same rule as generation |
| App behavior is actually broken | Product gap | Record it for the user. Keep it out of this PR |

### 6. Ship or stop

**changed:**

1. Re-read every changed file before committing.
2. Create a branch off the default branch (`verify-skill-maintenance-<date>`), commit only files inside the verify skill's directory, push, and open one PR with `gh pr create`.
3. The PR body lists: features covered, drift fixed (with the source citation that proved it), harness fixes and their re-proof evidence, `verified-unreachable` features with prerequisites, and product gaps found but not fixed.

If the user said not to open PRs, or there's no remote, stop at the local commit and say so.

**clean or blocked:** no branch, no PR. Report the outcome and the coverage honestly.

## Report

Whatever the outcome, tell the user in a few lines:

- the outcome (`clean`, `changed`, or `blocked`) and the PR link if there is one;
- features driven live versus `verified-unreachable`, with prerequisites;
- product gaps, each as one line with how to reproduce it. Offer to start a separate session for any worth fixing.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in your scratchpad directory, not in the repo. Don't commit them.
